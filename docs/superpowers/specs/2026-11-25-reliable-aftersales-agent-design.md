# 可靠售后 Agent：业务执行与政策判断设计

日期：2026-11-25。状态：用户已确认，已实现并完成本地验证；执行记录见 ../plans/2026-11-25-reliable-aftersales-agent.md。

## 目标与交付顺序

用户主要投 Agent / Python 后端岗位，已选择先实现可靠业务执行，再接入时态政策判断。
交付两个可独立验证的里程碑：A 可靠取消、退款申请、退货申请；B 有版本和证据的政策准入判断。
保留 FastAPI、LangGraph、SQLAlchemy、SQLite/PostgreSQL 与现有 Tool 接口，先复用当前 checkout。
工作区已有多处未提交改动；实现必须基于当前内容增量修改，不重置、覆盖或自动提交用户改动。

## 已核实的现状

- `ChatService._pending_actions` 使用进程内字典，过期判断采用 monotonic，重启和多实例不能共享。
- `IdempotencyRepository` 是先查再写，现有单测证明顺序复用，未证明独立连接并发下只有一次业务效果。
- Executor 执行写工具后，ChatService 最后提交聊天记录；模型生成和聊天持久化与写业务共用长事务。
- 取消订单已有状态检查，但读后再更新没有条件更新或锁保护；退款和退货缺少完整业务重复检查。
- SessionRepository 读取已有会话没有检查所属用户；请求体 user_id 目前不是认证身份。
- `RetrievedChunk.policy_version` 已存在；向量记录保存了版本，但检索入口、BM25、缓存没有完整的适用范围契约。
- 当前依赖 LangGraph 0.2.x；本次不依靠升级框架获得业务事务保证。

## 方案与取舍

1. 数据库业务状态机（本设计推荐）：共享操作记录、数据库原子争用和短事务；适合现有本地业务及后续远程接入。
2. 主要依靠 LangGraph checkpoint：可以恢复图状态，但不能独立解决业务并发、外部幂等和不确定结果；暂不作为主方案。
3. 引入消息队列与独立工作流引擎：适合更大规模异步流程，但当前先不引入运维依赖。

用户已选择“可靠业务执行后接政策判断”的产品方向。数据库状态机、以下接口和时间规则是实现建议，尚未被用户确认。

## A：持久化业务操作

### 操作记录与状态

新增 operations 表，至少保存：action_id、user_id、session_id、tool_name、规范化 arguments_json、
payload_hash、order_id、order_snapshot_hash、status、expires_at、created_at、updated_at、
执行代次、租约到期时间、provider、provider_idempotency_key、receipt_json、error_code、policy_evidence_json。
时间保存 UTC datetime；显式统一 SQLite 返回的 naive 时间与 aware 时间比较，不能持久化 monotonic。
参数哈希包含工具名、规范化参数和所属身份；客户端确认请求不能替换数据库中的参数。
新增 operation_events 表，保存状态迁移、时间、原因、trace_id、执行代次，不保存密钥或无关聊天全文。

状态为 PENDING_CONFIRMATION、READY、EXECUTING、SUCCEEDED、FAILED、EXPIRED、REQUIRES_RECONFIRMATION、UNKNOWN。

- PENDING_CONFIRMATION 经合法确认进入 READY；未确认前超时进入 EXPIRED。
- READY 被唯一执行者争用进入 EXECUTING；重复确认读取同一操作状态。
- 已知完成进入 SUCCEEDED，明确未完成且不可继续进入 FAILED。
- 确认时发现订单快照或政策依据改变，旧操作进入 REQUIRES_RECONFIRMATION，不执行，也不自动改成另一项操作。
- 远程结果不确定进入 UNKNOWN；UNKNOWN 只允许核对回执或人工处理，不能直接重新执行。
- 已成功操作即使超过原确认期限仍可查询和返回原回执。

READY 和 EXECUTING 对远程调用是持久化恢复点；本地写可以在同一事务中完成争用、检查、业务写入和成功迁移。
状态更新必须包含期望旧状态与执行代次，使用受影响行数检查，禁止旧执行者覆盖新状态。

### 事务与并发保证

提案入库成功后才返回待确认操作，不能在向客户端返回提案后才尝试保存。
写操作从模型推理和聊天保存事务中分离，操作服务自己拥有短事务及 session；避免让两个 AsyncSession 修改同一未提交资源。
历史准备事务先结束，再运行可能调用模型的规划；业务写使用独立短事务，最后再保存聊天记录。

本地执行事务依次完成：

1. 校验操作所属用户/会话、参数摘要、状态及确认期限，原子取得该操作执行权。
2. 对订单取得数据库写入排他权（PostgreSQL 行锁或等价条件更新；SQLite 使用等价的串行写入/条件更新）。
3. 在取得订单写入权之后读取最新状态和活动售后记录，比较已确认的快照，再判断业务条件。
4. 在同一事务写业务效果、操作成功回执和审计事件，提交后才返回成功。

同一 action_id 用数据库状态争用去重。不同 action_id 也必须通过订单级串行化与业务检查防止重复退款/退货。
远程操作另用数据库中的订单操作占用记录（order_id 唯一，关联 action_id）阻止不同操作同时出站；
占用在确认短事务中获得，UNKNOWN/未核对的 EXECUTING 不能释放，明确终态和业务结果落库后才释放。
该占用只能约束本系统发起的请求，不能阻止外部仓库自行发货；远程网关必须接收预期订单版本并在服务端验证，
不支持这项契约时，演示应明确不能保证跨系统条件检查与执行原子性。
取消只允许 CREATED/PAID；取消不是自动退款。退款申请不等于资金到账，限制重复活动退款；退货申请限制重复活动退货。
金额只从订单读取，以分保存。无法确定是否允许的状态拒绝执行，模型不得绕过这些条件。
本地写中途异常整体回滚；若需要记录失败，以新短事务记录，不把部分业务写提交。

里程碑 A 的演示业务准入规则明确如下（这是建议采用的保守业务设定，不是现有商家的真实规则）：

- cancel_order：仅 CREATED/PAID，且无阻塞售后记录。
- create_refund_request：仅 PAID/SHIPPED/DELIVERED，且无阻塞退款或退货记录；申请成功将订单置为 REFUNDING。
- create_return_request：仅 SHIPPED/DELIVERED，且无阻塞退款或退货记录；申请成功不代表资金变化。
- CREATED 不允许退款/退货；CANCELLED、REFUNDING、REFUNDED 不接受新取消、退款或退货申请。
- 售后记录只有 rejected、cancelled、failed 三种状态允许重新申请；requested、approved、processing、
  completed、succeeded、refunded 及未知状态均阻塞新的售后申请。已完成也阻塞，因为首版只做整单单次售后流程。
- 同一订单不同时开启退货和退款两个独立申请；“退货完成后再退款”的串联审核流程不在首版范围。
- 操作 FAILED 不代表业务记录已撤销；是否可重新申请仍由订单状态、售后记录和远程结果共同决定。
- 不同 action_id 的所有准入检查都在获得订单写入权后执行；第二个并发申请应读取第一个提交后的状态。

里程碑 B 的政策准入是上述技术/业务前置条件之外的附加条件，只能收紧，不能让 DENY 状态获得执行权。

### 远程接口与故障恢复

定义 BusinessGateway 的 submit(operation, stable_key) 与 lookup(stable_key) 接口；
lookup 必须区分 SUCCEEDED、PENDING、明确未受理、UNKNOWN、明确失败，网络错误不能解释为“未受理”。
首版提供持久化演示网关及测试替身，不接入真实支付/物流服务；演示网关按稳定 key 去重，回执跨对象重建可查询。
演示网关使用独立持久化存储和独立提交，避免本地事务回滚同时回滚“外部”效果，掩盖不确定结果问题。
远程成功后的本地业务投影、回执、操作成功状态及释放订单占用在同一个本地事务中写入，按 action_id 去重。
网关的能力声明必须写明是否支持幂等提交、可靠查询；缺少这些能力时不自动重发。

调用前独立提交 EXECUTING；调用期间不持有业务数据库事务或行锁。返回后再以短事务保存结果。
网关接收成功但客户端超时、进程崩溃、连接中断、无法可信解析响应时，保留 UNKNOWN 或过期 EXECUTING 等待核对。
恢复时先按稳定 key 查回执；确认成功则保存原回执；仍处理中则保留等待；只有网关契约允许、且明确未受理时才用同一 key 重发。
租约过期只表示需要核对，不能证明外部业务没有执行。提供有批次上限的恢复命令与管理员恢复入口，不在每个 API 进程启动时无控制扫描执行。
没有可查询或可去重契约时保持 UNKNOWN，说明需要人工核实，不宣称全局 exactly-once。

### API、Agent 和显示

保留 `/api/v1/chat`、`/chat/stream` 及 confirm_action_id 的交互方式，已有前端确认按钮继续可用。
增加 `GET /api/v1/actions/{action_id}`：仅可读取所属操作，返回状态、可公开回执、错误原因和政策证据。
增加独立确认入口 `POST /api/v1/actions/{action_id}/confirm`，聊天确认和该入口调用同一操作服务。
新增恢复命令；如提供恢复 HTTP 入口必须沿用管理员权限校验。
任何写工具无持久化确认记录时拒绝执行，即使直接构造图状态或填写 idempotency_key 也不能绕过。
单次提案只确认一个写操作，读工具仍复用当前执行及 fallback；写操作不走其他工具降级。

确认与状态查询使用数据库回执生成确定性展示，不因模型故障或重新分类把“已受理”改成“已到账”，或把 UNKNOWN 显示为失败。
成功提交后若聊天保存失败，操作状态与回执仍保留；客户端可查询/重试确认而不重复写。
SSE 在业务操作提交之后才发送最终成功信息；客户端断线不应撤销已经提交的业务效果。
新增结构化 action_result；pending_action 增加可选 expires_at 和 policy_evidence，现有字段保持兼容。

会话所属检查应在读取历史前执行。首版延续已有 demo user_id 输入，不宣称已经实现真实认证；
生产部署仍需要可信认证层绑定有效用户身份。新增 API 沿用同一身份解析入口，不能把会话所有权校验宣传为身份认证。

## B：接入政策判断

### 最小业务范围

先支持演示品类的整单退货/退款申请准入，涵盖普通商品与定制例外；不做分件退款、多币种或真实资金结算。
提供明确标注为演示业务规则的两个政策版本和对应源文档，不将生成政策当真实商家政策。
取消订单的状态条件由后端保证；政策决定能否提交申请，不代替人工审核或退款到账判断。

### 政策与证据

政策记录包含 policy_id、revision、valid_from、valid_to、applicability_basis、category、channel、
结构化准入规则、人工确定的优先级和 source_document/chunk/digest。生效区间采用左闭右开。
演示版选择 paid_at（缺失则 created_at）决定政策适用版本，delivered_at 决定退货期限；
这只是显式业务设定，不代表真实法律规则。时间缺失或例外事实不足时返回 NEEDS_INFORMATION。
结果为 ALLOW、DENY、NEEDS_INFORMATION、CONFLICT，并携带命中规则、事实来源和版本。
准入由确定性规则检查，LLM 负责解释；LLM 的答案不能授权写操作。
多个同优先级政策相互矛盾时返回 CONFLICT，不能用相似度分数挑一个。

新增只读工具 check_aftersale_eligibility。展示提案前检查，执行前再检查；所有写入口都必须经过同一准入服务。
提案冻结订单关键事实及政策证据摘要；如果执行时实际依据改变，不静默替换依据，要求重新发起确认。
重确认通过创建新 action_id 完成；旧操作不可复用。新旧政策发布改变不等于必然失效：仅当该订单的适用证据改变时失效。

### 与 RAG 的边界

使用带 snapshot_id 的不可变政策清单关联源文档；适用文档由政策服务选定，再进入检索和解释。
过滤必须在 BM25 和向量侧候选生成前生效，避免 top_k 被无效政策占满；内存向量与 Qdrant 的接口行为一致。
缓存键包含 snapshot_id、适用范围、query 和 top_k，引用包含 revision 与源内容摘要。
一次请求固定政策快照，已有提案保存可追溯的证据；源内容不匹配时不能用旧引用冒充当前政策。
首版政策快照通过显式发布/重新加载命令准备、验证、切换，保留旧快照供操作审计；
暂不做全知识库跨集群蓝绿发布平台。政策准入开关独立配置，启用时缺证据按信息不足处理，不能静默放行。
SQLite、离线模型与内存检索下必须能演示；后端准入不能依赖远程模型可用性。

## 验收与测试

里程碑 A：

- 提案入库后重建 ChatService，仍能确认；两个实例共享操作状态。
- 相同 action 并发确认、不同 action 同订单并发申请，最终业务效果符合去重约束。
- 并发测试使用独立连接的文件 SQLite；额外提供可选 PostgreSQL 集成测试，不能用单连接内存 SQLite 证明生产并发安全。
- 确认前发货、操作过期、跨用户/会话、伪造参数、同 key 异参均被拒绝；成功回执可以重放。
- 在业务写入后、成功状态保存前注入异常，本地事务不残留部分效果。
- 模拟网关成功但丢响应，查询得到原回执，业务效果保持一次；恢复时查询不可用仍保持 UNKNOWN。
- 进程在调用前后重启、租约过期、过时执行者回写均有确定性测试。
- 操作成功但模型/聊天保存失败时仍能查询成功；JSON/SSE 状态一致。

里程碑 B：

- 生效边界、旧单新政策、定制例外、缺失时间、冲突规则、多品类整单均有金标案例。
- 双路检索无不适用政策污染；缓存不跨快照和范围复用。
- 提案与执行之间政策适用依据改变，旧确认不执行；不影响该订单的政策变更不误拒绝。
- 模型不可用仍执行正确准入；政策允许也不能跳过人工确认。
- 固定测试集对比原版、范围过滤、冲突处理，公布分母、失败案例和实际运行条件，不沿用原项目数字作为改造成果。

运行针对性 pytest 后，再运行 Ruff、mypy、现有完整 pytest；修改前后记录已有失败。
迁移覆盖新建库与已有库；提供 SQLite/PostgreSQL 升降级验证，不能仅依靠 create_all 修改旧表。
不修改开发者 .env，不调用真实外部业务，不下载大模型权重作为正确性测试前提。
